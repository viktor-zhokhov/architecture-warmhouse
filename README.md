# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо управлять отоплением через REST API (`PATCH /api/v1/sensors/:id/value` — изменение статуса active/inactive).
- Система поддерживает полный CRUD для датчиков: создание (`POST /api/v1/sensors`), получение списка и по ID (`GET`), обновление (`PUT`), удаление (`DELETE`).
- Регистрация новых датчиков происходит через API специалистом на месте — пользователь не может подключить датчик самостоятельно.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру через `GET /api/v1/sensors` или `GET /api/v1/sensors/:id`.
- Система при каждом запросе синхронно обращается к внешнему сервису `temperature-api` (порт 8081) для получения актуальной температуры — pull-модель.
- Для каждого датчика выполняется отдельный HTTP-запрос (N+1 проблема).
- Отдельный эндпоинт `GET /api/v1/sensors/temperature/:location` возвращает температуру напрямую от temperature-api.
- Исторические данные не хранятся — только текущее значение при каждом запросе.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go 1.22
- **HTTP-фреймворк:** Gin v1.8.2
- **База данных:** PostgreSQL 16 (драйвер pgx/v5, connection pool)
- **Контейнеризация:** Docker (multi-stage build), Docker Compose
- **Архитектура:** Монолитная — вся логика в одном Go-бинарнике (`main.go` → `handlers/` → `services/` → `db/`).
- **Модель данных:** Единственная сущность `Sensor` с единственным типом `temperature`. Нет моделей User, House, DeviceType.
- **Таблица:** `sensors` (id, name, type, location, value, unit, status, last_updated, created_at).
- **Взаимодействие:** Синхронное — HTTP-вызовы к temperature-api. Нет очередей, событий.
- **Аутентификация:** Отсутствует. API полностью открыт.
- **Масштабируемость:** Ограничена — монолит нельзя масштабировать по частям.
- **Развёртывание:** Полная пересборка и перезапуск контейнера.

### 4. Проблемы монолитного решения

1. **N+1 проблема.** При `GET /api/v1/sensors` для каждого датчика — отдельный HTTP-запрос к temperature-api.
2. **Единственный тип устройства.** Только `temperature`. Добавление нового типа требует модификации всех слоёв.
3. **Нет пользователей и домов.** Нет аутентификации, API открыт — невозможна SaaS-модель.
4. **Pull-модель телеметрии.** Нет хранения истории, невозможны сценарии автоматизации.
5. **Единая таблица.** Невозможно масштабировать части системы независимо.
6. **Неделимый деплой.** Любое изменение — перезапуск всего приложения.
7. **Нет отказоустойчивости.** При недоступности temperature-api пользователь получает устаревшие данные без предупреждения.
8. **Нет устройств партнёров.** Жёсткая привязка к HTTP-протоколу temperature-api.
9. **Ручное подключение.** Выезд специалиста для каждой установки.
10. **Нет самообслуживания.** Пользователь не может подключить устройство сам.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
