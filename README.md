# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо управлять отоплением через REST API (`PATCH /api/v1/sensors/:id/value` — изменение статуса active/inactive).
- Система поддерживает полный CRUD для датчиков: создание (`POST /api/v1/sensors`), получение списка и по ID (`GET`), обновление (`PUT`), удаление (`DELETE`).
- Регистрация новых датчиков происходит через API специалистом на месте — пользователь не может подключить датчик самостоятельно.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру через `GET /api/v1/sensors` или `GET /api/v1/sensors/:id`.
- Система при каждом запросе синхронно обращается к внешнему сервису `temperature-api` (порт 8081) для получения актуальной температуры — pull-модель.
- Для каждого датчика выполняется отдельный HTTP-запрос (N+1 проблема).
- Отдельный эндпоинт `GET /api/v1/sensors/temperature/:location` возвращает температуру напрямую от temperature-api.
- Исторические данные не хранятся — только текущее значение при каждом запросе.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go 1.22
- **HTTP-фреймворк:** Gin v1.8.2
- **База данных:** PostgreSQL 16 (драйвер pgx/v5, connection pool)
- **Контейнеризация:** Docker (multi-stage build), Docker Compose
- **Архитектура:** Монолитная — вся логика в одном Go-бинарнике (`main.go` → `handlers/` → `services/` → `db/`).
- **Модель данных:** Единственная сущность `Sensor` с единственным типом `temperature`. Нет моделей User, House, DeviceType.
- **Таблица:** `sensors` (id, name, type, location, value, unit, status, last_updated, created_at).
- **Взаимодействие:** Синхронное — HTTP-вызовы к temperature-api. Нет очередей, событий.
- **Аутентификация:** Отсутствует. API полностью открыт.
- **Масштабируемость:** Ограничена — монолит нельзя масштабировать по частям.
- **Развёртывание:** Полная пересборка и перезапуск контейнера.

### 3. Определение доменов и границы контекстов

**Домен 1: Управление пользователями и домами**
*(в текущем коде отсутствует)*

- Поддомен: аутентификация и авторизация → контекст **Identity** (регистрация, логин, JWT, роли)
- Поддомен: управление домами → контекст **Home Management** (CRUD домов, привязка пользователей)

**Домен 2: Управление устройствами**
*(в текущем коде: только модель Sensor с типом `temperature`)*

- Поддомен: реестр устройств и типов → контекст **Device Registry** (каталог модулей и типов устройств, регистрация экземпляров, привязка к дому)
- Поддомен: управление состоянием → контекст **Device Control** (отправка команд, обратная связь)

**Домен 3: Телеметрия и мониторинг**
*(в текущем коде: данные не хранятся, pull-модель)*

- Поддомен: сбор телеметрии → контекст **Telemetry Ingestion** (приём данных от устройств, push-модель)
- Поддомен: предоставление данных → контекст **Telemetry Query** (API для текущих и исторических данных)

**Домен 4: Сценарии и автоматизация**
*(в текущем коде отсутствует. Выделен на основе требования To-Be: «пользователь настраивает сценарии работы»)*

- Поддомен: конструктор сценариев → контекст **Scenario Management** (CRUD сценариев, условия, действия)
- Поддомен: выполнение правил → контекст **Rule Engine** (оценка условий, выполнение действий)

**Домен 5: Уведомления**
*(в текущем коде отсутствует. Логически необходим для домена «Сценарии»: Rule Engine должен не только отправлять команды устройствам, но и информировать пользователя о срабатывании сценариев)*

- Контекст **Notification** (отправка push, email, SMS по событиям)

### 4. Проблемы монолитного решения

1. **N+1 проблема.** При `GET /api/v1/sensors` для каждого датчика — отдельный HTTP-запрос к temperature-api.
2. **Единственный тип устройства.** Только `temperature`. Добавление нового типа требует модификации всех слоёв.
3. **Нет пользователей и домов.** Нет аутентификации, API открыт — невозможна SaaS-модель.
4. **Pull-модель телеметрии.** Нет хранения истории, невозможны сценарии автоматизации.
5. **Единая таблица.** Невозможно масштабировать части системы независимо.
6. **Неделимый деплой.** Любое изменение — перезапуск всего приложения.
7. **Нет отказоустойчивости.** При недоступности temperature-api пользователь получает устаревшие данные без предупреждения.
8. **Нет устройств партнёров.** Жёсткая привязка к HTTP-протоколу temperature-api.
9. **Ручное подключение.** Выезд специалиста для каждой установки.
10. **Нет самообслуживания.** Пользователь не может подключить устройство сам.

# Задание 2. Проектирование микросервисной архитектуры

В этом задании вам нужно предоставить только диаграммы в модели C4. Мы не просим вас отдельно описывать получившиеся микросервисы и то, как вы определили взаимодействия между компонентами To-Be системы. Если вы правильно подготовите диаграммы C4, они и так это покажут.

**As-Is:** Текущая система — один монолит (Go + PostgreSQL), который объединяет все функции: управление датчиками, запрос температуры, хранение данных. Домен один — «Управление отоплением и мониторинг температуры».

**To-Be:** На основе 5 доменов из задания 1 выделены 5 микросервисов (bounded contexts объединены по доменам — Identity + Home Management → User Service, Device Registry + Device Control → Device Service, Telemetry Ingestion + Telemetry Query → Telemetry Service):

| Микросервис | Домен | Что делает |
|-------------|-------|-----------|
| User Service | Пользователи и дома | Регистрация, логин, JWT, CRUD домов |
| Device Service | Управление устройствами | Каталог модулей и типов, регистрация устройств, отправка команд |
| Telemetry Service | Телеметрия | Приём данных (MQTT), хранение истории, API чтения |
| Scenario Service | Сценарии | CRUD сценариев, Rule Engine, выполнение действий |
| Notification Service | Уведомления | Отправка уведомлений (email, SMS, push) |

Инфраструктура: API Gateway (Nginx), MQTT Broker, одна общая PostgreSQL.

Взаимодействие между микросервисами — REST/JSON. Связь с устройствами — MQTT.

# Задание 4. Создание и документирование API

### 1. Тип API

**REST API** (синхронное взаимодействие) — используется для всех коммуникаций: пользователь → API Gateway → микросервисы, и между микросервисами (Telemetry → Scenario, Scenario → Device, Scenario → Notification).

### 2. Документация API

[api-spec.yaml](./api-spec.yaml) — OpenAPI 3.0 спецификация.

**Внешний API** (через API Gateway, требует JWT):

| Эндпоинт | Метод | Сервис | Описание |
|----------|-------|--------|----------|
| /devices | POST | Device Service | Регистрация нового устройства |
| /devices/{id} | GET | Device Service | Получение информации об устройстве |
| /telemetry/{deviceId} | GET | Telemetry Service | Получение телеметрии (с фильтрацией по периоду) |
| /scenarios | POST | Scenario Service | Создание сценария автоматизации |
| /scenarios | GET | Scenario Service | Получение списка сценариев пользователя |
| /scenarios/{id} | DELETE | Scenario Service | Удаление сценария |

**Межсервисный API** (внутренняя сеть между микросервисами):

| Эндпоинт | Метод | Кто вызывает → Кто обрабатывает | Описание |
|----------|-------|--------------------------------|----------|
| /internal/devices/{id}/commands | POST | Scenario Service → Device Service | Отправка команды устройству при срабатывании сценария |
| /internal/events | POST | Telemetry Service → Scenario Service | Событие телеметрии (новое измерение) для проверки сценариев |
| /internal/notifications | POST | Scenario Service → Notification Service | Отправка уведомления пользователю |

Для просмотра спецификации можно использовать [Swagger Editor](https://editor.swagger.io/) — вставить содержимое файла api-spec.yaml.

# Задание 5. Работа с docker и docker-compose

### 1. Приложение temperature-api

[apps/temperature-api/main.go](./apps/temperature-api/main.go) — приложение на Go (без внешних зависимостей, только стандартная библиотека).

Эндпоинты:
- `GET /temperature?location=Living+Room` — температура по названию комнаты
- `GET /temperature/{sensorId}` — температура по ID датчика

При каждом вызове возвращает рандомное значение температуры (15–30°C). Маппинг location ↔ sensorId:
- "Living Room" ↔ "1"
- "Bedroom" ↔ "2"
- "Kitchen" ↔ "3"

Формат ответа соответствует `TemperatureResponse` из `smart_home/services/temperature_service.go`.

### 2. Dockerfile

[apps/temperature-api/Dockerfile](./apps/temperature-api/Dockerfile) — multi-stage build (golang:1.22-alpine → alpine). Порт 8081.

### 3. Docker Compose

[apps/docker-compose.yml](./apps/docker-compose.yml) — дополненный файл с настройками:

- **postgres**: environment (user, password), volume для данных, init.sql через docker-entrypoint-initdb.d (скрипт сам создаёт БД smarthome), healthcheck
- **temperature-api**: build из ./temperature-api, порт 8081
- **app**: без изменений (уже был настроен)

### Проверка

```bash
cd apps
docker-compose up --build
```

Затем в Postman:
1. Create Sensor — `POST http://localhost:8080/api/v1/sensors` с телом `{"name": "Living Room Temperature", "type": "temperature", "location": "Living Room", "unit": "°C"}`
2. Get All Sensors — `GET http://localhost:8080/api/v1/sensors` — при каждом вызове значение температуры будет разным.
